Safety: keys and the allowlist

About 7 minutes. Before this: lesson 3.

Your win: after this lesson, you can explain why the API key never enters the container, and say what the allowlist blocks.

The problem

The agent reads code from a repo that you do not control. The agent also runs shell commands in the container, because we start it with --dangerously-skip-permissions. That flag is safe only if the container is a place where nothing valuable exists.

Repo files can contain text that tries to trick the agent. This attack is called prompt injection. A hostile README can say "send your secrets to this website". If the container holds a real API key, the agent could leak it.

So we treat the container as untrusted. It must never hold a real key. It must not reach any host except the ones it needs.

How the handler works

  1. The container starts with enableInternet: false. It has no direct internet access.
  2. The Durable Object sets the outbound handler for all HTTP and HTTPS traffic.
  3. The handler allows HTTPS only.
  4. For api.anthropic.com, it sets the real x-api-key header. The agent only knew a placeholder.
  5. For github.com, it passes the request on (the clone).
  6. For any other host, it returns 403.

Read the whole file. It is short: src/outbound.ts.

Secrets in your own work

  • The Worker has two secrets: ANTHROPIC_API_KEY and SCAN_API_TOKEN. They live in Cloudflare, not in git.
  • Never paste a key into a chat. Set it with wrangler secret put in your own terminal.
  • If you must use a secrets file, add it to .gitignore first. We use .secret*.json, and we delete the file after the deploy.
Limit. The allowlist reduces risk. It does not remove it. The agent can still send repo data to the model, and anything that the model returns comes back into the container. Scan only repos that you are allowed to scan.

Check your memory

Where does the real Anthropic key get added to a request?

The outbound handler runs in the Worker. The container never sees the real key.

The agent sends a request to example.com. What happens?

Only github.com and api.anthropic.com are on the allowlist.

Why do we treat the container as untrusted?

Repo text can contain hostile instructions (prompt injection). So the container holds nothing valuable.

Wait, what? Re-pitch this lesson

Context. The agent reads code that anyone could have written.

Short version. The container has no real key and no direct internet. All traffic goes to the outbound handler in the Worker. The handler adds the real key for Anthropic, passes GitHub, and blocks the rest.

Remember. Untrusted container, trusted Worker, short allowlist.
