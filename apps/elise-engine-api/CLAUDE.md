# elise-engine-api

The scan Worker. Terms: `GLOSSARY.md`. Rules: `docs/standards/hono.md`, `docs/standards/effect.md`, `docs/standards/database.md`. Routes are mounted in `src/index.ts`.

- Two ways into `/scans/*` (`src/lib/require-scan-access.ts`): the shared `SCAN_API_TOKEN` plus an `x-account-id` the caller vouches for (the dashboard server), or a signed-in session whose user holds a Role in that account. `/auth`, `/sign-up`, `/me`, `/team` and `/groups` check for themselves.
- `/team` and `/groups` (`src/lib/require-power.ts`: a route asks for a Power from the access catalogue, and the role's grants decide), and a Repo's History (frozen, read for state only; one active scan per Repo): `docs/adr/0002-repo-history-and-team-management.md` before changing either.
- Branches (one History for each, the default as a pointer, the limit of 25, one-off Scans): `docs/adr/0004-repo-branches.md` before changing how a Scan finds its Branch.
- Private repos run on a Runner with the person's Git login: `docs/adr/0010-runner-git-login.md`. The cloud container clones public repos only, anonymously; the GitHub App path (ADR 0005) is retired.
- The Verdict (`/repos/:repoId/verdict`, accepted risks): `docs/adr/0003-ship-verdict.md` before changing the limits, the scan minimum or who may accept a risk.
- Full Scans (the lite and full paths, the profile caps and the one budget pool, Partial Scans, who may run full): `docs/adr/0006-full-worker-and-phase-budget.md` before changing a Scan's Skill path, a profile cap or a full limit.
- Runner login (`/runners/login/*`, the dashboard's `/device` page, `platform_runner_device_logins`): `docs/adr/0007-runner-login-own-device-flow.md` before changing how a Runner gets its token. A Runner never holds a person's session.
- Source providers (`src/providers/*`, Upload apps and Archives): `docs/adr/0008-git-providers.md` before changing where a Scan's code comes from. Core reads a provider only through `#/providers/registry` and `#/providers/port` (lint enforces it), and a request with no `provider` means `github`.
- The Trace (`src/modules/scan-trace`, `GET /scans/:scanId/trace`, `POST /runners/jobs/:scanId/trace`): `docs/adr/0009-trace-labels-only.md` before changing what a Trace entry holds. It holds labels only, never model content.
- Live findings (`src/modules/live-findings`, `POST /runners/jobs/:scanId/findings`): `docs/adr/0013-live-findings-early.md` before changing what a running Scan may send early. Only verified records; the result replaces them, a stopped or failed Scan drops them.
- Bring your own key (`src/modules/anthropic-key`, `/usage/anthropic-key`): an account may store its own Anthropic key, sealed with AES-GCM under `KEY_ENCRYPTION_SECRET` and bound to the account ID. The workflow's `prepare` step reads the sealed key and passes it in the `Outbound` props; `Outbound` opens it per model call and never falls back to the platform key if it will not open. No key row means the platform key.
- A scan runs as Workflow -> Sandbox Durable Object -> container: `FullScanWorkflow` -> `FullScanSandbox` -> container (`Dockerfile.full`, the full Skill only). It is the only path: every new Scan is stored `skill: full` and starts on it, a Runner Scan included, and the request's `skill` is ignored. The lite Skill, Workflow (`ScanWorkflow`), Sandbox (`ScanSandbox`) and Image are gone (#141), and old `lite` rows stay readable. A Scan that is running keeps the class it started on, so never rename `FullScanSandbox` or `FullScanWorkflow`. A scan in our cloud runs four Phases, `recon`, `hunt`, `check` and `report`, each a separate run of the agent with its own files (`phaseAgentFiles`) and its own time slot, all sharing the one meter that holds the Scan's whole Budget cap (`scan-sandbox/utils/meter.ts`), and a Phase is not a Step. A Runner scan runs the same four Phases (the app starts one `claude` run for each, on the Phase prompts in its job, or one run on the single prompt when the job has none), spends from one pool that the app holds, takes no credit and holds none, needs an active Plan (the Runner plan, paid through Stripe: `src/modules/stripe`, `/usage/plan/checkout` with a `planKey`, `/usage/plan/portal`, `/usage/plan/change` for a move between plans; only the webhook changes a Subscription), has `RUNNER_MAX_BUDGET_USD` as its ceiling, and counts only on `MAX_ACTIVE_SCANS` (`limitPathOf`), never on the full cap. The Anthropic key stays in the Worker: the container reaches the network only through `Outbound`, which asks `SANDBOX_FULL` for the Scan's meter.
- Neon is the record of every scan (`scans`, `scan_files`, `scan_findings` in `packages/db-elise`): the API reads state, usage and file names only from there. R2 holds the file bytes under the account and Scan ID, and each object has a `scan_files` row with its key and size, so nothing in the bucket is untracked. Only the names in `SCAN_SERVABLE_FILES` are served. `GET /files` (`src/modules/files`) lists the written ones across scans; the list and the download both refuse a key outside `accounts/{accountId}/`.
- `skills/*` are the scan agent's prompts, so every line costs tokens on every scan. The dashboard parses the `findings.json` they define (`elise-frontend-web/.../finding-schemas.ts`): change both together.
- Request and response shapes live in `@repo/contracts/elise`. Responses use the `{ data, error }` envelope.
- Scans fail in local `wrangler dev` on Apple Silicon (`RangeError: Out of memory`), and a deploy that fails with `meta.db: input/output error` has a damaged Docker store: `docs/ops.md` before debugging either. Test scans on the deployed Worker.
- Local: `wrangler dev` needs Docker for the container. Secrets: `ANTHROPIC_API_KEY`, `SCAN_API_TOKEN`, `DATABASE_URL`, `AUTH_SECRET`, `KEY_ENCRYPTION_SECRET` (optional: without it an account cannot save its own Anthropic key), and `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` (without them checkout and the webhook fail). A Scan takes its cap from its profile (`SCAN_PROFILE_CAPS_USD` in `src/constants/scan-constants.ts`, provisional), which a request may lower, never raise; `MAX_BUDGET_FULL_USD` guards that table. `MAX_ACTIVE_SCANS` limits a Runner's live Scans per Account, `MAX_ACTIVE_FULL_SCANS` its live Scans in our cloud. There is no limit over all Accounts.
- `pnpm check` is `tsc` on the source, `tsc -p tsconfig.test.json` on source and tests, oxlint and vitest (vitest does not type-check). The oxlint `anti-slop` rules are strict: lint right after the first edit. Read test failures through `pnpm check:apps` (it trims them); a raw `vitest run` prints whole SQL statements and parameter lists.
- Side effects enter through `AppDeps` (`src/types/variables.ts`, real ones in `src/lib/app-deps.ts`): session lookup, role check, monthly spend, scan ledger. Route tests build the app with `testDeps({ ...only the deps the test changes })` (`src/__tests__/test-deps.ts`, with in-memory fakes such as `memory-scan-repo.ts`), so a new dep is added there once; query tests run on pglite with every migration (`src/__tests__/test-db.ts`). No module mocking: the lint bans it.
- Lint rules that bite on the first write: a route has no `try`/`catch`/`finally` (use `withPool` or a service); Promise work sits inline in `Effect.tryPromise({ try, catch })`, never in a bare `async`; an exported effect declares `Effect.Effect<A, E>`; a cast needs a `// SAFETY:` line; a comment is a `// -----` block or nothing; parse a response with a zod schema, never `typeof` checks; a helper returns its inferred type, not `Record<string, string>`; a test helper that captures nothing sits at module scope; the engine has no Node types, so use WebCrypto and `atob`, never `node:crypto` or `Buffer`.
- Usage numbers (`scans.cost_usd` and friends) come from the agent's own report, and the cost is an estimate: `docs/usage-cost.md` says how to check it.
