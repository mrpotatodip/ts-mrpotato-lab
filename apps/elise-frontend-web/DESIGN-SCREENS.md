# elise-frontend-web: screens

What each screen shows and why. Read it with `DESIGN.md` (tokens, layout, components, shared patterns, the design standard) when you review or change one of these screens. Every rule here is as mandatory as the rules there.

- **Overview** leads with what to decide, as the branch page does, and puts the scan history after it: three rows, 32px between cards, and the same header on every card (a 15px title and one 14px line).
  1. **Running now**, only while a scan is queued or running: one row each with the repository, the branch and commit (`ScanOrigin`), the status and when it started, linking to the live report. It is gone when nothing runs, because the "In progress" state is also in the sidebar and the scan list behind it polls only while a scan is active.
  2. The repository summary as one strip (`RepoSummaryStrip`): open findings as the 40px lead number, then came back, needs a person and not re-checked (the same four answers as the tiles on `/repos`), with no icon chips or tints. Then **Where to look first** (`RepoAttentionList`: every repository, most urgent first, each with one reason and a link, and a quiet "Clear" for one with nothing open) beside **Recent scans** (four rows with branch and commit; a succeeded scan is quiet text with a check, and only running, queued and failed are coloured pills).
  3. The monthly budget, the success rate and the scan activity (a quarter, a quarter and a half of the width, so the 14 day buttons stay at least 24px apart).
  - The scan-count tiles (total, in progress, succeeded, failed) and the severity breakdown card were removed: the success ring already says succeeded and failed, and the summary strip already shows the severity dots.
  - The summary and the attention list come in as `ScanOverview` slots from the route, because the scan module does not import the repository module (`oxlint.config.ts` enforces the direction).
  - A value of 0 is muted. **Colour marks the exception on this page**: the ring, the budget bar and the succeeded bars are neutral, red appears for a failure (the failed count, the failed bars, a tight budget), blue for a running scan, and the severity dots carry the findings. Do not colour the normal case.
- **Stat card** (`ShellStatTile`, on `/repos` and the scan report): label and an icon tile (tinted by meaning) on one row, a 34px number, then one muted line of context derived from real data. A value of 0 is muted so the tiles with something to act on stand out.
- **Scan activity chart**: a stacked bar per day for the last 14 days (succeeded in `mark-neutral`, failed, in progress), dashed gridlines with a value axis, and a tooltip on every bar that lists the day and its counts. Each bar is a labelled button, so keyboard and screen-reader users get the same numbers. The data is derived from the scans list; the chart needs no endpoint.
- **Success ring**: an SVG ring with the percentage in the middle and a neutral arc, then succeeded and failed as plain figures. The failed figure is red only while it is above 0.
- **Severity chart** (not on the overview; kept for a screen that needs it): a segmented bar for share, then one row per severity with dot, label, `Progress` bar, count and percent. Colour is never the only signal: every row has a text label and a number.
- **Lists**: a repository is shown as muted `owner/` plus the `name` in full weight. Times are short (`Nov 8, 10:12 AM`) in muted tabular numerals.
- **Status panels** on a scan page are `Alert`s: failed is the destructive variant with the engine's message; queued and running is the info variant with a spinner.
- **Scan report** (`ScanDetail`) is written for the person who has to decide what to do: a header with the status, the branch the scan read (or "One-off scan" for a pasted commit, as on the branch page) and a link to that branch's history (the repository's when the scan has no branch), run facts as labelled pairs (kind of review, model, effort, started, took, code read), four summary tiles (findings, needs a person, new since last scan, cost), a findings table whose rows open a side sheet with the impact, evidence, suggested fix and what to check in one column, a one-line "ready to ship?" strip under the summary tiles (the answer, the next step and a link to the branch page, where the full verdict is read and acted on, because the answer belongs to the commit and not to one scan; a one-off scan has no branch page, so it keeps the full card), and a "what changed" card that groups findings as came back, new, not re-checked, still open and fixed. Each group says what it means and what to do. Not re-checked is a warning: treat those as still open. Raw values (`lite`, `low`) never appear as labels: use the option copy in `constants/`.
- **Scan list** rows answer "what did it find and cost" without opening: the branch and commit under the repository, findings with severity dots, a "to check by hand" count, review kind and model, cost. Older scans load with "Load older scans"; the header shows `N+` while more exist.
- **Repositories** follow the same rule: decide first, browse second. A repository is a plain heading and each tracked **branch** under it is the link.
  - **List** (`/repos`): the same `RepoSummaryStrip` as Overview across every repository (open findings as the lead number, came back, needs a person, not re-checked), then one group per repository, sorted by what needs attention. The heading shows scan count, latest status and time. Each branch is a row linking to its page, with a "Default" tag. Only the default branch row shows open counts, because the engine's list carries only those; other rows say "Open the branch to see its findings". A repository with no branch has one "No branch tracked yet" row. "Add repository" opens a dialog (repository link, optional branch names, "n of 25") that scans nothing and checks nothing on GitHub; it is safe to repeat for a repository that exists.
  - **Branch page** (`/repos/$repoId/branches/$branchId`, ids not names): `/repos/$repoId` redirects to the default branch, or to `?branch=NAME` from a list link. The header holds the repository, a branch chip (a "Switch branch" select when the repository has two or more branches), "Open branch on GitHub" and "Scan this branch". Facts are the branch's latest scan, the commit read and its scan count. The four tiles count that branch. Findings open in the side sheet (impact, evidence, fix, state, where first seen or fixed, and the decision select, also kept inline on each row), with a search and a state filter that shows a count per state. The scan history lists only this branch's scans (older scans with no branch count as the default branch's) and says how many others are hidden. A failed scan says why in one line (`scanFailure`).
  - **No branch**: the page says to run a scan or add the repository again with branch names.
- **Decisions and status** (`modules/finding`): a finding has two truths, what scans found (open, came back, fixed by a scan) and what a person decided (open, fixed, false positive, accepted risk). The reader gets one answer from both (`findingStatusKey`): a scan that proved a fix wins, then a person's decision, then the scan state. The status badge says it in a word ("Fixed by a scan", "Marked fixed", "False positive", "Risk accepted", "Came back", "Open"), the row shows who decided and when under the decision select, and the sheet opens with a status banner (what happened, who, when, what it means next, and the reason or note). A finding a scan fixed shows no select: no decision is needed. "Marked fixed" says plainly that no scan has confirmed it, and that a later scan finding it again shows as Came back. The repository list filters follow the same grouping as the Open findings tile (needs action, decided by a person, fixed by a scan, every finding), each with a count, so the list and the tile never disagree. **Accepted risk** opens a dialog for a reason and a duration (7 to 90 days), says what will happen in a sentence, and is only enabled for account admins (the option shows "Account admins only" for others). A decision updates the row at once; the counts refresh in the background.
- **Files viewer**: `Tabs` (mono pills, selected pill tinted, arrow-key navigation) over an inset `pre` with mono text. An empty file shows "This file is empty."
- **New scan** is a dialog (`ScanNewDialog`), opened from the topbar, from the empty state of the scans list, and as "Scan again" on a repository page. It never asks for a link the account already has: the repository field is a select of repositories already scanned (newest first, each with its last result), and "A different repository" reveals the link field. With none scanned, the link field shows at once. A branch select follows ("Default branch", "Default branch (not scanned yet)" while unknown, each tracked branch, "Other…" for a typed name; for a typed link it is a free field). "Scan this branch" opens it with that repository and branch chosen. A repository with a queued or running scan shows a warning and disables "Start audit", because the engine allows one active scan per repository. A bad link moves focus to the link field. In demo screens it never calls the engine and shows "This is a demo, so no audit was started."
