# elise-frontend-web: screens

What each screen shows and why. Read it with `DESIGN.md` (tokens, layout, components, shared patterns, the design standard) when you review or change one of these screens. Every rule here is as mandatory as the rules there.

- **Overview** leads with what to decide, as the branch page does, and puts the scan history after it: three rows, 32px between cards, and the same header on every card (a 15px title and one 14px line).
  1. **Running now**, only while a scan is queued or running: one row each with the repository, the branch and commit (`ScanOrigin`), the status and when it started, linking to the live report. It is gone when nothing runs, because the "In progress" state is also in the sidebar and the scan list behind it polls only while a scan is active.
  2. The repository summary as one strip (`RepoSummaryStrip`): open findings as the 40px lead number, then came back, needs a person and not re-checked (the same four answers as the tiles on `/repos`), with no icon chips or tints. Then **Where to look first** (`RepoAttentionList`: every repository, most urgent first, each with one reason and a link, and a quiet "Clear" for one with nothing open) beside **Recent scans** (four rows with branch and commit; every status, succeeded included, is a pill).
  3. The monthly budget, the success rate and the scan activity (a quarter, a quarter and a half of the width, so the 14 day buttons stay at least 24px apart).
  - The scan-count tiles (total, in progress, succeeded, failed) and the severity breakdown card were removed: the success ring already says succeeded and failed, and the summary strip already shows the severity dots.
  - The summary and the attention list come in as `ScanOverview` slots from the route, because the scan module does not import the repository module (`oxlint.config.ts` enforces the direction).
  - A value of 0 is muted. **Colour follows the status on this page**: the ring, the succeeded figure and the succeeded bars are green, red appears for a failure (the failed count, the failed bars, a tight budget), blue for a running scan, and the severity dots carry the findings. The budget bar stays neutral until it is tight.
- **Stat card** (`ShellStatTile`, on `/repos` and the scan report): label and an icon tile (tinted by meaning) on one row, a 34px number, then one muted line of context derived from real data. A value of 0 is muted so the tiles with something to act on stand out.
- **Scan activity chart**: a stacked bar per day for the last 14 days (succeeded in `mark-success`, failed, in progress), dashed gridlines with a value axis, and a tooltip on every bar that lists the day and its counts. Each bar is a labelled button, so keyboard and screen-reader users get the same numbers. The data is derived from the scans list; the chart needs no endpoint.
- **Success ring**: an SVG ring with the percentage in the middle and a green arc, then succeeded and failed as figures. The succeeded figure is green and the failed figure red, each only while it is above 0.
- **Severity chart** (not on the overview; kept for a screen that needs it): a segmented bar for share, then one row per severity with dot, label, `Progress` bar, count and percent. Colour is never the only signal: every row has a text label and a number.
- **Lists**: a repository is shown as muted `owner/` plus the `name` in full weight. Times are short (`Nov 8, 10:12 AM`) in muted tabular numerals.
- **Private repositories carry one marker, the same everywhere** (`GithubPrivateBadge`): a "Private" outline badge with a lock in headings (the repository list, the repository and branch pages, the scan report), and the lock alone, small and muted, in dense rows (the scan lists and the sidebar tree), with "Private repository" for a screen reader and on hover. A branch has no marker of its own: it is private because its repository is. A public repository, and one no connection covers, show nothing, because the marker is the exception (`DESIGN.md` Restraint). It reads the repository's last answer from GitHub (`isPrivate`) in the repository screens, and the scan's own answer in the scan screens, so an old scan keeps what was true when it ran. The Files list does not show it yet.
- **Status panels** on a scan page are `Alert`s: failed is the destructive variant with the engine's message; queued and running is the info variant with a spinner.
- **Scan report** (`ScanDetail`) is written for the person who has to decide what to do, and is laid out like the branch page it belongs to: answer first, then what changed, then the list.
  - **Header**: the repository (muted `owner/`, the name in full weight) and the Private badge when it applies, then the branch as a chip (the way to that branch's history, with a button that opens the branch on GitHub), or "One-off scan" for a pasted commit with a link to the repository's history. Under it one calm line, as on the branch page: the status, when it started, how long it took, and the commit it read, a link to GitHub. "Scan this branch again" (or "Scan again" for a one-off scan) sits on the right and opens the new-scan dialog on that repository and branch. Kind of review, model and effort are not in the header.
  - **Body, in order**: the four summary tiles (findings, needs a person, new since last scan, cost); the full **Ready to ship?** card, the same card and decision control as the branch page (the answer belongs to the commit, not to one scan, and it says so); two alerts when they apply, in the branch page's words, **came back after being fixed** (red) and **not re-checked by this scan** (amber, treat as still open); the **What changed** card, which groups findings as came back, new, not re-checked, still open and fixed, each group saying what it means and what to do; the findings table, whose rows open a side sheet with the impact, evidence, suggested fix and what to check in one column; **Scans of this branch**, the latest five scans of the same branch with this one marked and not a link, hidden for a one-off scan, for a branch with no other scan, and in the demo screens; **Run details**, a closed card with the kind of review, the model and the effort; and the **Files** tabs.
  - A scan that is queued, running or failed shows its notice, then Run details. Raw values (`lite`, `low`) never appear as labels: use the option copy in `constants/`.
- **Scan list** and **Files** show a scan's status the same way as every other screen (`ScanStatusBadge`): a pill for every state, a green one for succeeded. The column is "Status" on the list and "Scan status" on Files.
- **Scan list** rows answer "what did it find and cost" without opening: the branch and commit under the repository, findings with severity dots, a "to check by hand" count, review kind and model, cost. Older scans load with "Load older scans"; the header shows `N+` while more exist.
- **Repositories** follow the same rule: decide first, browse second. A repository is a plain heading and each tracked **branch** under it is the link.
  - **List** (`/repos`): the same `RepoSummaryStrip` as Overview across every repository (open findings as the lead number, came back, needs a person, not re-checked), then one group per repository, sorted by what needs attention. The heading shows scan count, latest status and time. Each branch is a row linking to its page, with a "Default" tag. Only the default branch row shows open counts, because the engine's list carries only those; other rows say "Open the branch to see its findings". A repository with no branch has one "No branch tracked yet" row. "Add repository" opens a dialog (repository link, optional branch names, "n of 25") that scans nothing and checks nothing on GitHub; it is safe to repeat for a repository that exists.
  - **Branch page** (`/repos/$repoId/branches/$branchId`, ids not names): `/repos/$repoId` redirects to the default branch, or to `?branch=NAME` from a list link. The header holds the repository, a branch chip (a "Switch branch" select when the repository has two or more branches), "Open branch on GitHub" and "Scan this branch". Facts are the branch's latest scan, the commit read and its scan count. The four tiles count that branch. Findings open in the side sheet (impact, evidence, fix, state, where first seen or fixed, and the decision select, also kept inline on each row), with a search and a state filter that shows a count per state. The scan history lists only this branch's scans (older scans with no branch count as the default branch's) and says how many others are hidden. A failed scan says why in one line (`scanFailure`).
  - **No branch**: the page says to run a scan or add the repository again with branch names.
  - **Private repositories** need a connection, which lives on **Connections**, not here. "Add repository" says so beside the link field ("Private repository? Connect GitHub first", a link to `/connections`), gets a picker of the connected repositories above the link field (hidden when there are none), and pasting a link always still works. A private repository shows a "Private" tag next to its name in the list and on its page.
- **Connections** (`/connections`, `modules/github`; visible to every member, and one sidebar item with no children until a second provider exists, as Repositories has no chevron with one repository): where EliseLAB reads code from. A page header, then a **GitHub** card, then a **Repositories EliseLAB can read** card. The GitHub card (and `/github/callback`) shows who the account is connected as (name, "All" or "Selected repositories", the date, a status pill) with a "Manage on GitHub" link on each install (the engine asks GitHub again when its last check is over five minutes old, so a removed or suspended install shows as such), a "Disconnect" button on each install for account admins only (a dialog says EliseLAB stops using it, past scans stay, and that access is removed in GitHub's own settings), and, for admins only, a "Connect GitHub" button (or "Connect another account") that sends the browser to GitHub. Other members read a sentence that asks an admin to connect it. GitHub sends the browser back to `/github/callback`, an admin-only page that saves nothing until the person ticks the notice (code excerpts go to Anthropic) and presses "Finish connecting"; it keeps **Connections** active in the sidebar, its breadcrumb reads Connections, Finish connecting GitHub, and saving returns to `/connections`. The second card lists the repositories the active connections can read (first 100, a "Private" tag on private ones, a search from six rows) and is hidden until a connection is active; it says what to do when the list is empty.
- **Team** (`/team`, `modules/team`; account admins only, and anyone else is sent to Overview): who can use the account. A page header ("Who can use this account, and how they are grouped."), then a **People** card and a **Groups** card. People is a table of name and email, role, and Groups, with a "You" tag on the signed-in person, an invite button that opens a dialog (the invite is emailed, and the dialog also shows the link once as a copy), and the invites still waiting, each with its Groups, a "Resend" button (a new email and link; the earlier link stops working) and a "Revoke" button that asks to confirm. Groups lists the named sets of people. A Group grants nothing: access comes from the Role.
- **Sign in and sign up** (`/signin`, `/signup`, `modules/auth`; the invite pages `/invite/$token` share the mark, the corner theme button and the card width): pages with no shell. From 1024px up they are two columns inside a `max-w-6xl` frame: a brand panel (`AuthBrandPanel`: the EliseLAB mark and name, one headline and three plain lines on what EliseLAB does) and the form card (`max-w-lg`, 32px padding, 20px between fields). Below 1024px the panel is hidden and the mark and name sit above the card (`ShellPublicBrand`). The mark (`ShellLogo`) is an "E" of three bars in `--primary` and `--primary-foreground`, so it flips with the theme. A theme button sits in the top right corner (`ShellPublicThemeSwitch`); the pages carry `data-public-page`, so in Moonlight the sky starts at the top, as there is no top bar. The panel and the name take the page header's text halo, so they stay readable on the sky. Field errors say what to type ("Enter your email address."), never the rule that failed; focus moves to the first field with an error. The words are in `modules/auth/constants/auth-copy.ts`.
- **Decisions and status** (`modules/finding`): a finding has two truths, what scans found (open, came back, fixed by a scan) and what a person decided (open, fixed, false positive, accepted risk). The reader gets one answer from both (`findingStatusKey`): a scan that proved a fix wins, then a person's decision, then the scan state. The status badge says it in a word ("Fixed by a scan", "Marked fixed", "False positive", "Risk accepted", "Came back", "Open"), the row shows who decided and when under the decision select, and the sheet opens with a status banner (what happened, who, when, what it means next, and the reason or note). A finding a scan fixed shows no select: no decision is needed. "Marked fixed" says plainly that no scan has confirmed it, and that a later scan finding it again shows as Came back. The repository list filters follow the same grouping as the Open findings tile (needs action, decided by a person, fixed by a scan, every finding), each with a count, so the list and the tile never disagree. **Accepted risk** opens a dialog for a reason and a duration (7 to 90 days), says what will happen in a sentence, and is only enabled for account admins (the option shows "Account admins only" for others). A decision updates the row at once; the counts refresh in the background.
- **Files viewer**: `Tabs` (mono pills, selected pill tinted, arrow-key navigation) over an inset `pre` with mono text. An empty file shows "This file is empty."
- **Files** (`/files`, `modules/file`): the written reports of every scan, newest first. It lists `REPORT.md`, `FINDINGS-DETAIL.md` and `NEEDS-VALIDATION.md`; the machine-readable files stay on the scan page. The type tabs ("Report", "Finding details", "To check by hand") each show how many files they would list under the other filters, and a type with none is dimmed. A line under the tabs says what the chosen type holds and that dates and times are in UTC; the Saved column is UTC too, so it matches the filters. Filters are a repository select, a branch select (once a repository is chosen), From and To days in UTC, and a repository search sent with Enter. They live in the URL, so a view can be shared. The file name and size never wrap. Below `lg` the Scan and Size columns drop out, and below `md` Branch and Saved too: the repository cell then carries the branch and time. Each Download names its file, repository, branch, UTC time and the end of the scan ID for a screen reader, so no two share a name. "Clear filters" shows once: in the filter row while files are listed, in the empty state when nothing matches.
- **New scan** is a dialog (`ScanNewDialog`), opened from the topbar, from the empty state of the scans list, and as "Scan again" on a repository page. It opens with one question, "Is the repository public or private?", as two choice cards (not in demo screens). **Public** is the flow below and lists only repositories not known to be private. **Private** replaces the repository block with dropdowns fed by the GitHub connection: a repository select (the repositories EliseLAB can read, a lock on private ones), then a branch select that opens on "Default branch" with the real default's name under it, then the branches (first 100, a hint when there are more), and "Other…" to type a branch, tag or commit. With no connection it shows a "No GitHub connection yet" note that links to Connections, and "Start audit" stays disabled until a repository is chosen. A branch that fails to load says so and points to Connections, and "Other…" still works. Opened on a private repository ("Scan again"), the dialog starts on Private with that repository chosen. Public never asks for a link the account already has: the repository field is a select of repositories already scanned (newest first, each with its last result), and "A different repository" reveals the link field. With none scanned, the link field shows at once. A branch select follows ("Default branch", "Default branch (not scanned yet)" while unknown, each tracked branch, "Other…" for a typed name; for a typed link it is a free field). "Scan this branch" opens it with that repository and branch chosen. A repository with a queued or running scan shows a warning and disables "Start audit", because the engine allows one active scan per repository. A bad link moves focus to the link field. In demo screens it never calls the engine and shows "This is a demo, so no audit was started."
