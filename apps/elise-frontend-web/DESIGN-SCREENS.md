# elise-frontend-web: screens

What each screen shows and why. Read it with `DESIGN.md` (tokens, layout, components, shared patterns, the design standard) when you review or change one of these screens. Every rule here is as mandatory as the rules there.

- **Overview** leads with what to decide, as the branch page does, and puts the scan history after it: three rows, 32px between cards, and the same header on every card (a 15px title and one 14px line).
  1. **Running now**, only while a scan is queued or running: one row each with the repository, the branch and commit (`ScanOrigin`), the status and when it started, linking to the live report. It is gone when nothing runs, because the "In progress" state is also in the sidebar and the scan list behind it polls only while a scan is active.
  2. The repository summary as one strip (`RepoSummaryStrip`): open findings as the 40px lead number, then came back, needs a person and not re-checked (the same four answers as the tiles on `/repos`), with no icon chips or tints. Then **Where to look first** (`RepoAttentionList`: every repository, most urgent first, each with one reason and a link, and a quiet "Clear" for one with nothing open) beside **Recent scans** (four rows with branch and commit; every status, succeeded included, is a pill).
  3. The monthly budget, the success rate and the scan activity (a quarter, a quarter and a half of the width, so the 14 day buttons stay at least 24px apart).
  - The scan-count tiles (total, in progress, succeeded, failed) and the severity breakdown card were removed: the success ring already says succeeded and failed, and the summary strip already shows the severity dots.
  - The summary and the attention list come in as `ScanOverview` slots from the route, because the scan module does not import the repository module (`oxlint.config.ts` enforces the direction).
  - A value of 0 is muted. **Colour follows the status on this page**: the ring, the succeeded figure and the succeeded bars are green, red appears for a failure (the failed count, the failed bars, a tight budget), blue for a running scan, and the severity dots carry the findings. The budget bar stays neutral until it is tight.
- **Security status** (`/summary`, `modules/summary`; every signed-in member, linked under Overview) is a read-only page for people who watch the workspace and do not work in the findings. A **Watcher** (a login that holds the Summary Power and not the Dashboard Power, `isWatcher`) sees nothing else: every other page redirects to `/summary`, the sidebar lists only Security status, the topbar has no "New scan" button, and the layout does not load the scan list. It answers "where does each repository stand" before anything else: a header, the same `RepoSummaryStrip` as Overview, then one **Repositories** card with a row per repository in the same urgency order as "Where to look first" (`rankRepos`). A row with something open reads as a link (a chevron, the repository and its default branch, then the severity dots, "N need a person" for the open findings the agent could not confirm and so carry no severity, "N open" and a status pill) and opens that repository's page; a repository with nothing to read is a plain row. There is no accordion.
  - **Repository page** (`/summary/$repoId`, `modules/summary`; same audience; the id is the repository's, and one this account does not hold shows the app's "Page not found"): the breadcrumb is Security status, then the repository. A header with the repository name, its default branch and its status pill; the same `RepoSummaryStrip`, for this repository alone; then an **Open findings** card. Every open finding on the default branch is written out in full, none hidden: a severity badge and a state badge ("Confirmed", "Came back" or "Needs a person to check"), a "Copy link" button, the title (`h3`), and "What could happen", "How it gets fixed" and, for an unconfirmed one, "What a person needs to check". Each finding has its own address, `/summary/$repoId#finding-<id>`: "Copy link" puts it on the clipboard, and opening it scrolls to the finding and marks it with a 3px bar in `--primary`. More than a page of findings loads with "Show more findings".
  - Each row names the repository and its default branch, and ends with one status: **Clear** (nothing open), **Needs attention** (anything open, with a red "came back" count when a fixed problem returned) or **Not scanned yet**. The status comes from the repository list alone (`repoStatus`); there is no ship verdict yet, because it needs one extra request per repository.
  - Only a row that needs attention opens. The first such row starts open. Its findings load when it opens (the default branch, open findings only; fixed, dismissed and accepted risks are not shown), so the page itself is one cached request.
  - A finding shows its severity, its state in plain words (Confirmed, Needs a person to check, Came back) and its title. **Details** holds the impact and the fix, plus what a person needs to check when the finding needs one. Evidence, file paths and the actor are never shown, and nothing on the page links into the technical screens or changes anything.
  - Loading is a skeleton shaped like the page; a repository whose findings fail to load shows the error inside its own row with "Try again". The wording is the scan's own, so it is still written for engineers: a plain-language rewrite is not part of this page.
- **Stat card** (`ShellStatTile`, on `/repos` and the scan report): label and an icon tile (tinted by meaning) on one row, a 34px number, then one muted line of context derived from real data. A value of 0 is muted so the tiles with something to act on stand out.
- **Scan activity chart**: a stacked bar per day for the last 14 days (succeeded in `mark-success`, failed, in progress), dashed gridlines with a value axis, and a tooltip on every bar that lists the day and its counts. Each bar is a labelled button, so keyboard and screen-reader users get the same numbers. The data is derived from the scans list; the chart needs no endpoint.
- **Success ring**: an SVG ring with the percentage in the middle and a green arc, then succeeded and failed as figures. The succeeded figure is green and the failed figure red, each only while it is above 0.
- **Severity chart** (not on the overview; kept for a screen that needs it): a segmented bar for share, then one row per severity with dot, label, `Progress` bar, count and percent. Colour is never the only signal: every row has a text label and a number.
- **Lists**: a repository is shown as muted `owner/` plus the `name` in full weight. Times are short (`Nov 8, 10:12 AM`) in muted tabular numerals.
- **Private repositories carry one marker, the same everywhere** (`GithubPrivateBadge`): a "Private" outline badge with a lock in headings (the repository list, the repository and branch pages, the scan report), and the lock alone, small and muted, in dense rows (the scan lists and the sidebar tree), with "Private repository" for a screen reader and on hover. A branch has no marker of its own: it is private because its repository is. A public repository, and one no connection covers, show nothing, because the marker is the exception (`DESIGN.md` Restraint). It reads the repository's last answer from GitHub (`isPrivate`) in the repository screens, and the scan's own answer in the scan screens, so an old scan keeps what was true when it ran. The Files list does not show it yet.
- **Status panels** on a scan page are `Alert`s: failed is the destructive variant with the engine's message; queued and running is the info variant with a spinner.
- **Scan report** (`ScanDetail`) is written for the person who has to decide what to do, and is laid out like the branch page it belongs to: answer first, then what changed, then the list.
  - **Header**: the repository (muted `owner/`, the name in full weight) and the Private badge when it applies, then the branch as a chip (the way to that branch's history, with a button that opens the branch on GitHub), or "One-off scan" for a pasted commit with a link to the repository's history. Under it one calm line, as on the branch page: the status, when it started, how long it took, and the commit it read, a link to GitHub. "Scan this branch again" (or "Scan again" for a one-off scan) sits on the right and opens the new-scan dialog on that repository and branch. Kind of review, model and effort are not in the header.
  - **Body, in order**: the four summary tiles (findings, needs a person, new since last scan, cost; a scan that ran on a Runner reads "What it would cost" and says it ran on that computer, so nothing was billed); the full **Ready to ship?** card, the same card and decision control as the branch page (the answer belongs to the commit, not to one scan, and it says so); two alerts when they apply, in the branch page's words, **came back after being fixed** (red) and **not re-checked by this scan** (amber, treat as still open); the **What changed** card, which groups findings as came back, new, not re-checked, still open and fixed, each group saying what it means and what to do; the findings table, whose rows open a side sheet with the impact, evidence, suggested fix and what to check in one column; **Scans of this branch**, the latest five scans of the same branch with this one marked and not a link, hidden for a one-off scan, for a branch with no other scan, and in the demo screens; **Run details**, a closed card with the kind of review, the model and the effort; and the **Files** tabs.
  - A scan that is queued, running or failed shows its notice, then Run details. Raw values (`lite`, `low`) never appear as labels: use the option copy in `constants/`.
- **Scan list** and **Files** show a scan's status the same way as every other screen (`ScanStatusBadge`): a pill for every state, a green one for succeeded. The column is "Status" on the list and "Scan status" on Files.
- **Scan list** rows answer "what did it find and cost" without opening: the branch and commit under the repository, findings with severity dots, a "to check by hand" count, review kind and model, cost. Older scans load with "Load older scans"; the header shows `N+` while more exist.
- **Repositories** follow the same rule: decide first, browse second. A repository is a plain heading and each tracked **branch** under it is the link.
  - **List** (`/repos`): the same `RepoSummaryStrip` as Overview across every repository (open findings as the lead number, came back, needs a person, not re-checked), then one group per repository, sorted by what needs attention. The heading shows scan count, latest status and time. Each branch is a row linking to its page, with a "Default" tag. Only the default branch row shows open counts, because the engine's list carries only those; other rows say "Open the branch to see its findings". A repository with no branch has one "No branch tracked yet" row. "Add repository" opens a dialog (repository link, optional branch names, "n of 25") that scans nothing and checks nothing on GitHub; it is safe to repeat for a repository that exists.
  - **Branch page** (`/repos/$repoId/branches/$branchId`, ids not names): `/repos/$repoId` redirects to the default branch, or to `?branch=NAME` from a list link. The header holds the repository, a branch chip (a "Switch branch" select when the repository has two or more branches), "Open branch on GitHub" and "Scan this branch". Facts are the branch's latest scan, the commit read and its scan count. The four tiles count that branch. Findings open in the side sheet (impact, evidence, fix, state, where first seen or fixed, and the decision select, also kept inline on each row), with a search and a state filter that shows a count per state. The scan history lists only this branch's scans (older scans with no branch count as the default branch's) and says how many others are hidden. A failed scan says why in one line (`scanFailure`).
  - **No branch**: the page says to run a scan or add the repository again with branch names.
  - **Private repositories** need a connection, which lives on **Connections**, not here. "Add repository" says so beside the link field ("Private repository? Connect GitHub first", a link to `/connections`), gets a picker of the connected repositories above the link field (hidden when there are none), and pasting a link always still works. A private repository shows a "Private" tag next to its name in the list and on its page.
- **Connections** (`/connections`, `modules/github`; visible to every member, and one sidebar item with no children until a second provider exists, as Repositories has no chevron with one repository): where Elise reads code from. A page header, then a **GitHub** card, then a **Repositories Elise can read** card. The GitHub card (and `/github/callback`) shows who the account is connected as (name, "All" or "Selected repositories", the date, a status pill) with a "Manage on GitHub" link on each install (the engine asks GitHub again when its last check is over five minutes old, so a removed or suspended install shows as such), a "Disconnect" button on each install for account admins only (a dialog says Elise stops using it, past scans stay, and that access is removed in GitHub's own settings), and, for admins only, a "Connect GitHub" button (or "Connect another account") that sends the browser to GitHub. Other members read a sentence that asks an admin to connect it. GitHub sends the browser back to `/github/callback`, an admin-only page that saves nothing until the person ticks the notice (code excerpts go to Anthropic) and presses "Finish connecting"; it keeps **Connections** active in the sidebar, its breadcrumb reads Connections, Finish connecting GitHub, and saving returns to `/connections`. The second card lists the repositories the active connections can read (first 100, a "Private" tag on private ones, a search from six rows) and is hidden until a connection is active; it says what to do when the list is empty.
- **Team** (`/team`, `modules/team`; roles that hold `company:team:members:read` (account admin and workspace admin), and anyone else is sent to Overview): who can use the account. A page header ("Who can use this account, and how they are grouped."), then a **People** card and a **Groups** card. People is a table of name and email, role, and Groups, with a "You" tag on the signed-in person, an invite button that opens a dialog (the invite is emailed, and the dialog also shows the link once as a copy), and the invites still waiting, each with its Groups, a "Resend" button (a new email and link; the earlier link stops working) and a "Revoke" button that asks to confirm. Groups lists the named sets of people. A Group grants nothing: access comes from the Role.
- **Settings** (`/settings`, `modules/settings`; roles that hold `company:usage:budget:update` (account admin and workspace admin), and anyone else is sent to Overview, with no sidebar item): how the account pays for scans. In the sidebar it is an item with three pages under it, open while the reader is in Settings (one icon when the sidebar is collapsed): **Budget** (`/settings/budget`), **Providers** (`/settings/providers`, needs `company:usage:anthropic_key:update`, and without it the reader lands on Budget) and **History** (`/settings/history`). `/settings` goes to Budget. **Providers** holds an **Anthropic API key** card: it says whose key the scans use ("Elise's key" by default, or "Your own key" with `sk-ant-…` and its last four characters and the save date), with "Use my own key" (or "Replace key") that opens an inline form (`AnthropicKeyForm`: one masked field, tested with Anthropic before saving, never shown again) and, for an own key, "Remove key". A scan already running keeps the key it started with. Under it, a **Runners** card (`modules/runner`) lists the computers that may run this account's scans: a row for each with its name, one line on what to do next or when it was last seen, and a status pill (Waiting for pairing, Code expired, Connected). "Add a runner" opens a dialog that asks one question ("What is this computer called?"), then shows the pairing code once, large and in mono, with the time it expires and "Copy code"; the list polls every 4 seconds while a code is waiting, so the row turns to Connected when the app pairs. "Remove" asks first and says what stops (a connected computer stops at once). An account with none shows an empty state with the next step. **History** holds a **Recent changes** card: the last 20 changes to the budget and the key, newest first, each with who and when in UTC (a key line shows its last four characters, never the key). **Budget** holds the **Monthly budget** card. The page header reads "What this account may spend on scans each month." Monthly budget leads with the budget in large type and a "Change budget" button that opens an inline form (`UsageBudgetForm`): one dollar field, the allowed range under it ("Between $5.00 and $100.00": at least what the month has spent or holds for running scans, at most the most the account may set), Save and Cancel. Below it: spent this month, held by running scans, remaining, and "Most you can set", with a line to contact Elise for more. A budget line in History reads from what to what (the default is shown as "the default"). A person whose login is gone reads "Someone who has since left". Everyone else still sees the budget on Overview.
- **Sign in, sign up and password reset** (`/signin`, `/signup`, `/forgot-password`, `/reset-password?token=`, `modules/auth`; "Forgot your password?" on sign-in opens the request page, which swaps its form for one line that is the same for every email; the emailed link opens the reset page, and a spent or missing token says so and offers a new link; the invite pages `/invite/$token` share the mark, the corner theme button and the card width): pages with no shell. From 1024px up they are two columns inside a `max-w-6xl` frame: a brand panel (`AuthBrandPanel`: the Elise mark and name, one headline and three plain lines on what Elise does) and the form card (`max-w-lg`, 32px padding, 20px between fields). Below 1024px the panel is hidden and the mark and name sit above the card (`ShellPublicBrand`). The mark (`ShellLogo`) is an "E" of three bars in `--primary` and `--primary-foreground`, so it flips with the theme. A theme button sits in the top right corner (`ShellPublicThemeSwitch`); the pages carry `data-public-page`, so in Moonlight the sky starts at the top, as there is no top bar. The panel and the name take the page header's text halo, so they stay readable on the sky. Field errors say what to type ("Enter your email address."), never the rule that failed; focus moves to the first field with an error. The words are in `modules/auth/constants/auth-copy.ts`.
- **Decisions and status** (`modules/finding`): a finding has two truths, what scans found (open, came back, fixed by a scan) and what a person decided (open, fixed, false positive, accepted risk). The reader gets one answer from both (`findingStatusKey`): a scan that proved a fix wins, then a person's decision, then the scan state. The status badge says it in a word ("Fixed by a scan", "Marked fixed", "False positive", "Risk accepted", "Came back", "Open"), the row shows who decided and when under the decision select, and the sheet opens with a status banner (what happened, who, when, what it means next, and the reason or note). A finding a scan fixed shows no select: no decision is needed. "Marked fixed" says plainly that no scan has confirmed it, and that a later scan finding it again shows as Came back. The repository list filters follow the same grouping as the Open findings tile (needs action, decided by a person, fixed by a scan, every finding), each with a count, so the list and the tile never disagree. **Accepted risk** opens a dialog for a reason and a duration (7 to 90 days), says what will happen in a sentence, and is only enabled for account admins (the option shows "Account admins only" for others). A decision updates the row at once; the counts refresh in the background.
- **Files viewer**: `Tabs` (mono pills, selected pill tinted, arrow-key navigation) over an inset `pre` with mono text. An empty file shows "This file is empty."
- **Files** (`/files`, `modules/file`): the written reports of every scan, newest first. It lists `REPORT.md`, `FINDINGS-DETAIL.md` and `NEEDS-VALIDATION.md`; the machine-readable files stay on the scan page. The type tabs ("Report", "Finding details", "To check by hand") each show how many files they would list under the other filters, and a type with none is dimmed. A line under the tabs says what the chosen type holds and that dates and times are in UTC; the Saved column is UTC too, so it matches the filters. Filters are a repository select, a branch select (once a repository is chosen), From and To days in UTC, and a repository search sent with Enter. They live in the URL, so a view can be shared. The file name and size never wrap. Below `lg` the Scan and Size columns drop out, and below `md` Branch and Saved too: the repository cell then carries the branch and time. Each Download names its file, repository, branch, UTC time and the end of the scan ID for a screen reader, so no two share a name. "Clear filters" shows once: in the filter row while files are listed, in the empty state when nothing matches.
- **New scan** is a dialog (`ScanNewDialog`), opened from the topbar, from the empty state of the scans list, and as "Scan again" on a repository page. It has a title and no description, and opens on one search field ("Search your repositories or paste a GitHub link"): there is no question about public or private. Under it the list shows every repository the account can scan, in a Public group and a Private group, filtered as the person types. A private row has a lock and a "Private" tag, and each row says its last result or that it is connected on GitHub. The arrow keys walk the field and the rows, and Enter takes the first. A pasted GitHub link (with or without `https://`) shows as a "Scan owner/name" row on top, and a link to a repository the account already has answers with that repository, not a duplicate. With no active GitHub connection a line under the list says an admin connects GitHub on Connections to scan a private repository. Until the GitHub connection's repositories have arrived the list shows placeholders (it cannot tell which scanned repositories are private, and rows that move are worse than a short wait), and "Start audit" waits too; a pasted link shows at once. Choosing a repository replaces the list with a card: the repository, "Public repository" or "Private repository" and "Change", which returns to the search, with a labelled "Branch" select on its own row so a long branch name is never cut. The card follows the list: a repository chosen before the connection's repositories arrive is shown as private once they do. The branch select opens on "<default> (default)", then the other branches, then "Other…" to type a branch, tag or commit. A public repository the account scanned reads its branches from the engine, a private one reads them from GitHub through its connection (first 100, with a hint when there are more), and a pasted link has no list, so a field takes the branch, tag or commit. A branch list that fails to load says so and offers the typed field. "Scan again" and "Scan this branch" open the dialog on the card, with that repository and branch chosen. Below the card, "Quick review" and "Full audit" are two cards of one line each. Full adds a "Coverage" segmented control (Focused, Balanced, Exhaustive) with the chosen one's description under it. One line of chips says where the audit runs, the model and the effort, and "Customize" replaces the chips with the same three as selects: "Run on" appears only for a public repository when a runner is connected. A repository with a queued or running scan shows a warning and disables "Start audit", because the engine allows one active scan per repository. A summary of what is about to run is read to screen readers. In demo screens it never calls the engine and shows "This is a demo, so no audit was started."
